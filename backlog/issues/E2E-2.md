## Context

ADR 0003, « The first Appareil »: the browser that shows the install command becomes the first trusted Appareil. The Runner and the browser exchange their public keys through the server and each proves it knows the 128-bit secret of the link code with an HMAC-SHA256 over both keys, so our own server cannot swap a key (SEC-4). The browser then creates the vault key (one AES-256 key per Pilote) and wraps it for the Runner and for itself. Every later encrypted thing (Sessions, SESSION-1; Idées, IDEE-1) depends on it.

## Current state of the code

- Created by RUNNER-3: link codes `apps/server/src/runners/link/` with the opaque `browserPairing` (sent at `POST /api/runner/link-codes`), `runnerPairing` (`POST /api/runner/link/:linkId/pairing`), the confirm `POST /api/runner/link-codes/:id/confirm { pairing }` and the binary's poll `GET /api/runner/link/:linkId` returning the browser's confirm pairing with the token; `crewdeck-runner link`; the page `/demarrage` that draws the secret.
- Created by E2E-1: `apps/web/src/keys/crypto.ts` (X25519, `hpkeSeal`/`hpkeOpen`, AES-GCM, HMAC, constant-time compare), `apps/web/src/keys/base32.ts`, `apps/runner/internal/keys/` (the same in Go), `docs/security/e2e.md`, `packages/contracts/fixtures/crypto/`.
- Created by RUNNER-2: `apps/runner/internal/state/` (`~/.crewdeck/`).
- No Appareil, no vault key.

## Decisions already made

- The proofs bind the short id and both public keys in a fixed order; labels distinguish the two directions, so one proof can never be replayed as the other.
- The server stores only public keys and wraps; it never receives the secret, the vault key nor an item key. A test fails if a request body of the link flow contains the secret's base32 (e2e request recording).
- One vault key per Pilote, versioned (`vaultKeyVersion`); rotation is E2E-4.
- Linking a new Runner when the Pilote already has a vault (the new Runner replaces the old): the confirming browser must be a trusted Appareil; it opens its own wrap and wraps the existing vault key for the new Runner only (`deviceVaultWrap` absent). An untrusted browser cannot confirm: the server refuses with 422 `devices.not-trusted` and the page says « Approuve d'abord cet Appareil depuis un Appareil de confiance. » (E2E-3 builds the approval).
- Another browser signing in later has no vault key until E2E-3 approves it: it sees `vaultState: 'no-device'` (E2E-3 builds the approval).

## Acceptance criteria

- [ ] A full link (fake binary in the integration test driving the Go `link` against the server, the web pairing code under Vitest) ends with a trusted Appareil, a Runner, two wraps of version 1, and the same vault key opened on both sides (proved by sealing an item in the browser and opening it in Go, and back).
- [ ] A server that swaps the device public key it hands to the Runner makes the Runner refuse; one that swaps the Runner's public key makes the browser reject with `pairing-mismatch` and the page shows its Banner and a new command.
- [ ] Relinking a Runner from a trusted Appareil wraps the existing vault key for the new Runner (same key, version unchanged); from an untrusted browser the confirm gets 422 `devices.not-trusted`.
- [ ] The secret and the vault key never appear in any request or stored column (asserted).
- [ ] The device private key is non-extractable (`exportKey` throws); `runner.key` and `vault.wrap` are mode 600.
- [ ] `GET /api/devices` and `GET /api/devices/:id/vault-key-wrap`: nominal matches schemas; 401 without a session; 404 for another Pilote's Appareil; 422 `devices.revoked`, `devices.not-trusted`.
- [ ] `device.upserted` is written in the confirm's transaction.
