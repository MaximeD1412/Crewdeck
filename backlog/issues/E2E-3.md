## Context

ADR 0003, « A new Appareil »: the phone (or any new browser) shows a QR code carrying its own 128-bit secret, scanned by an Appareil already trusted (or its text copied into it); the same HMAC proof runs, and the trusted Appareil wraps the vault key for the new one. Without any trusted Appareil: `crewdeck-runner appareils approuver <code>`, the code pasted from the new Appareil. No short code is ever typed: a secret short enough to type could be ground offline by the server. Until it is approved, a browser signed in to the account cannot read Sessions nor the text of the Idées (US-60). Having a second Appareil early is also what keeps the Idées' text from being lost (risk OPS-1).

There is no mockup for this flow: it is composed of the existing Composants (Dialog, Banner, Card, ListRow, Button, CodeBlock, TextField) in the default Skin, and reviewed through its captures.

## To do

- **Contracts** `packages/contracts/src/api/devices.ts` (extend): `NewDeviceRequest` `{ publicKey, name, proof }` with `proof = HMAC-SHA256(secret, "crewdeck/v1/device/new" ‖ publicKey)`; `PendingDevice` `{ id, shortId, name, publicKey, proof, expiresAt }`; `ApproveDevice` `{ approver: { type: 'device'|'runner', id }, wrap: { enc, ciphertext }, proof, seq? }` with `proof = HMAC-SHA256(secret, "crewdeck/v1/device/approve" ‖ newPublicKey ‖ approverPublicKey)` and the wrap sealed for the new public key with `aad = deviceId ‖ vaultKeyVersion`.
- **Server** `apps/server/src/devices/`:
  - `POST /api/devices` (session) → `201 { id, shortId, expiresAt }`: a `pending` Device with `shortId` (4 Crockford characters, unique among pending), the proof, `expiresAt` = 10 min; at most 3 pending per Pilote (422 `devices.too-many-pending`).
  - `GET /api/devices/pending/:shortId` (session) → `PendingDevice` (404 unknown or expired).
  - `POST /api/devices/:id/approve` (session, from a trusted Appareil: `X-Crewdeck-Device` must be trusted, else 422 `devices.not-trusted`) body `ApproveDevice`: stores the wrap for the current `vaultKeyVersion`, the approver's proof, marks the Device `trusted`; 409 if not `pending`; `device.upserted`.
  - Runner routes (Bearer): `GET /api/runner/devices/pending/:shortId` and `POST /api/runner/devices/:id/approve` (approver `runner`).
  - `GET /api/devices/:id/approval` (session, the new Appareil) → `{ approver: { type, id, publicKey }, proof }` once trusted, so it can verify who wrapped its key.
- **Web** `apps/web/src/keys/approval.ts` and the dialogs `apps/web/src/dialogs/device-approval.ts` (the product's own, outside the Skin registry like `crewdeck-confirm`, ADR 0006):
  - New Appareil: when `vaultState` is `no-device`, the Cadre's `banner` shows a caution Banner « Cet Appareil ne lit pas encore tes Sessions ni le texte de tes Idées. » with « Approuver cet Appareil ». The dialog generates the key pair and the secret, registers the pending Device, shows the QR code of `crewdeck:appareil:<shortId>-<secret>` (library `qrcode`, rendered to a canvas), the same code as text with « Copier », the alternative `crewdeck-runner appareils approuver <code>` in a CodeBlock, and the remaining time; on `device.upserted` trusted, it fetches `approval`, verifies the approver's proof over the approver's public key, opens its wrap, and says « Appareil approuvé ». Expired: « Code expiré » and « Recommencer ».
  - Trusted Appareil: an « Appareils » card on `/parametres` (between « Notifications » and « Planifications ») listing the Pilote's Appareils (name, « autorisé le 3 nov. », « cet Appareil » for the current one) and « Ajouter un Appareil »; the dialog offers « Scanner » (camera through `getUserMedia` and `BarcodeDetector`, shown only where `BarcodeDetector` exists) or a TextField « Colle le code affiché sur le nouvel Appareil »; then fetches the pending Device, verifies its proof, asks « Approuver « <name> » ? », wraps the vault key (`rawVaultKeyForWrap()`) and approves.
  - When the Pilote has exactly one trusted Appareil, the « Appareils » card shows a caution Banner « Un seul Appareil lit tes données chiffrées : ajoute ton téléphone pour ne rien perdre. » (OPS-1).
  - Copy keys `devices.*`.
- **Runner**: `crewdeck-runner appareils approuver <code>`: fetch the pending Device, verify its proof, print its name and ask « Approuver « <name> » ? (o/N) », wrap the vault key with `internal/keys/vault.go` and approve.
- `docs/security/e2e.md`: section « New Appareil » with the exact bytes.
- Scenarios `apps/server/src/testing/scenarios/devices.ts` (`appareil-a-approuver`, `appareils`), Playwright `apps/web/e2e/devices.spec.ts` with two browser contexts (the trusted one approving the new one by pasting the code), at 390 and 1280 px with axe.

## Decisions already made

- No mockup exists for this flow (a design gap noted in the design journal): the dialogs follow `design/DESIGN.md` (Dialog, one primary action, French copy, tutoiement) and the « Appareils » card follows the Paramètres page's cards; the captures go through the visual review.
- The code is never typed: QR code or copy-paste, 4 + 26 characters (ADR 0003).
- The approval dialogs are the core's, not Composants: no Skin can replace them (like the Action sensible's confirmation).
- The Notifications card's device rows (push subscriptions, ATOI-4) are distinct from the Appareils (key holders).

## Acceptance criteria

- [ ] A new browser context signed in to the account shows the Banner, registers a pending Appareil and shows the QR code and the code; the trusted context approves it by pasting the code; the new context opens the vault (seals and opens an item that the trusted one opens too).
- [ ] A server that swaps the new Appareil's public key, or the approver's, makes the verification fail on the other side and nothing is approved (unit tests with a tampering fake).
- [ ] `crewdeck-runner appareils approuver <code>` approves a pending Appareil (integration test with the Go binary).
- [ ] An expired or used code is refused (404/409) and the dialog says so.
- [ ] Routes: nominal matches schemas; 400 with `fields`; 401; 404 for another Pilote's Appareil; 409 not pending; 422 `devices.not-trusted`, `devices.too-many-pending`.
- [ ] The secret never appears in a request (recorded requests).
- [ ] With one trusted Appareil, the card shows the OPS-1 Banner; with two, not.
- [ ] The flow passes Playwright at 390 and 1280 px with axe; captures for the visual review.
