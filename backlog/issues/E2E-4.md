## Context

ADR 0003, « Revoking an Appareil » (from the Paramètres) rotates the vault key: the next Appareil or Runner online rewraps the item keys under the new one; the server stops serving ciphertext to the revoked one at once. « Losing every key holder (Runner reinstalled and no Appareil left) loses the Idées' text: the product says so before the last revocation » (risk OPS-1). A Runner replaced by a new link (RUNNER-3) is a revoked key holder too.

## Current state of the code

- Created by E2E-3: the « Appareils » card on `/parametres` (list, « Ajouter un Appareil »), `apps/web/src/dialogs/device-approval.ts`, the approval routes.
- Created by E2E-2: `Device`, `VaultKeyWrap` (per holder and `vaultKeyVersion`), `pilot.vaultKeyVersion`, `apps/web/src/keys/vault.ts` (`sealItem`/`openItem`: a random item key wrapped by the vault key), `apps/runner/internal/keys/vault.go`, the `X-Crewdeck-Device` header.
- Created by RUNNER-3: linking a new Runner revokes the old (`runners.revokedAt`).
- No revocation, no rotation. No encrypted item exists yet at this milestone (Idées come with IDEE-1), so the rotation's item registry starts empty.

## To do

- **Server** `apps/server/src/devices/`:
  - `POST /api/devices/:id/revoke` body `{ seq }` → the Device `revoked` (`revokedAt`), its wraps deleted, `pilot.vaultRotationPending = true`, `device.upserted`, in one transaction. Revoking the current Appareil is allowed (its page then clears IndexedDB and shows the Banner of E2E-3).
  - From then on, every route serving a wrap or a stored ciphertext refuses a revoked `X-Crewdeck-Device` with 422 `devices.revoked`; a guard `TrustedDeviceGuard` applied to those routes (E2E-2's wrap route now; IDEE-1 applies it to the Idées' ciphertext).
  - A Runner revoked by a new link also sets `vaultRotationPending` and deletes its wraps.
  - `GET /api/vault` → `{ version, rotationPending, holders: [{ type, id, publicKey }] }` (the trusted Appareils and the current Runner) and `GET /api/vault/items?cursor=` → the wrapped item keys to rewrap `{ items: [{ itemType, itemId, wrappedKey }], nextCursor }`, from a registry `VaultItemsRegistry` (`register(itemType, { list(pilotId, cursor), replace(pilotId, itemId, wrappedKey) })`) that IDEE-1 fills.
  - `POST /api/vault/rotations` body `{ fromVersion, toVersion: fromVersion + 1, wraps: [{ holderType, holderId, enc, ciphertext }], items: [{ itemType, itemId, wrappedKey }], seq }`: atomically stores the new wraps, replaces the item keys, sets `vaultKeyVersion`, clears `rotationPending`; 409 `vault.version-changed` if `fromVersion` is not current; 422 `vault.holders-missing` unless `wraps` covers every current holder; 422 `vault.items-missing` unless `items` covers every registered item. Large vaults: the body is bounded at 10 MB (an Idée's item key is 60 bytes).
  - The Runner's wrap of the new version reaches it on `hello.accepted` (and a `vault.rotated` protocol message while connected).
- **Web** `apps/web/src/keys/rotation.ts`: a trusted, unlocked Appareil that sees `rotationPending` (state slice) rotates: draws a new vault key, opens every item key with the old one and wraps it with the new one, wraps the new vault key for each holder, posts the rotation; on 409 it reloads the vault and retries once.
- **Runner** `apps/runner/internal/keys/rotation.go`: the same when the Runner is the first holder online with `rotationPending` (via `hello.accepted`), using `GET /api/vault*` and `POST /api/vault/rotations` with its Bearer token.
- **Revocation in the page**: each row of the « Appareils » card gets « Retirer »; the core's `crewdeck-confirm` dialog (not an Action sensible, a product dialog) says what happens; when the Appareil is the last trusted one, it adds « C'est ton dernier Appareil de confiance : si tu réinstalles ensuite le Runner, le texte de tes Idées sera perdu. »; `crewdeck-runner uninstall` (RUNNER-8) prints the same warning when no trusted Appareil exists.
- `docs/security/e2e.md`: section « Revocation and rotation ».

## Decisions already made

- Either a trusted Appareil or the Runner may rotate; the first one online does it. Until then the old version keeps working for the remaining holders; only the revoked one is cut off, at once, by the server.
- Session keys are per Session and wrapped only for trusted holders when a Session opens (SESSION-1): a revoked Appareil gets none from then on; nothing to rewrap.
- The rotation is one transaction: either every holder and item moves to the new version, or nothing does.

## Acceptance criteria

- [ ] Revoking an Appareil makes its next wrap request answer 422 `devices.revoked` at once and marks the rotation pending, with its event.
- [ ] A trusted Appareil then rotates: the version increments, every remaining holder opens the new key, an item sealed before opens after the rotation (Vitest with a registered test item type).
- [ ] The Runner rotates when it is the first online holder (integration test with the Go side).
- [ ] A rotation missing a holder or an item is refused with its 422; a concurrent rotation gets 409 `vault.version-changed`.
- [ ] Revoking the last trusted Appareil shows the warning first; revoking the current one clears its IndexedDB.
- [ ] Routes: nominal matches schemas; 400; 401; 404 for another Pilote's Appareil.
